# Incident Report: Legacy v1 Agent Installation Failure and Incorrect Node Binding

- Date: 2026-08-05
- Status: Resolved
- Affected component: Legacy v1 portal-generated Unix installation command

## 中文

### 事件摘要

旧版 v1 Portal 在“服务器管理”中生成的 Unix 安装命令无法下载探针脚本，`wget` 返回 `404 Not Found`。修复下载地址并完成安装后，新服务器仍未出现在对应的监控节点下。

### 影响

- 新服务器无法通过 Portal 生成的命令完成初次安装。
- 使用错误节点的安装命令后，新服务器的探针绑定到了已有节点，导致目标新节点没有监控数据。
- 错误绑定还可能使已有节点的数据被另一台服务器覆盖或交替上报。

### 根因

1. v1 Portal 将安装脚本地址写死为：

   ```text
   https://raw.githubusercontent.com/kadidalax/cf-vps-monitor/main/cf-vps-monitor.sh
   ```

   上游 `main` 分支升级到 v2 后，仓库根目录不再包含 `cf-vps-monitor.sh`。因此旧 Portal 继续生成了已经失效的 URL。

2. 修复下载后，安装命令是从已有服务器的行中复制的。命令中的 `-s/--server-id` 和 API Key 属于已有节点，而不是新建节点，所以新服务器没有上报到预期位置。

### 修复措施

1. 将 v1 Portal 的 `baseScriptUrl` 固定到仍包含旧版脚本的不可变 Release：

   ```text
   https://github.com/kadidalax/cf-vps-monitor/releases/download/v1.0.2/cf-vps-monitor.sh
   ```

2. 重新部署 Worker，使 Portal 复制出的命令直接使用上述 Release 地址。
3. 停止错误绑定的探针，从新建服务器对应的 Portal 行重新复制安装命令。
4. 确认新命令中的服务器 ID 和 API Key 均属于目标新节点，再重新安装并启动探针。

### 验证

- Release 下载地址可以正常跳转并返回完整脚本。
- 下载的脚本通过 `bash -n` 语法检查。
- 线上 Portal 的 `admin.js` 已返回修正后的 Release 地址。
- 使用正确节点生成的命令重新安装后，新节点开始上报监控指标。

### 预防措施

- 旧版安装器必须固定到不可变的 Release 或提交，不应引用持续变化的 `main` 分支路径。
- CI 应定期验证 Portal 生成的下载 URL 返回成功状态并且文件非空。
- Portal 的复制成功提示应同时显示服务器名称和服务器 ID，降低复制错误节点命令的风险。
- 安装器应在执行前明确打印目标 Worker、服务器名称和服务器 ID，并要求确认或提供非交互式校验选项。
- 故障排查时先检查 `$HOME/.cf-vps-monitor/config` 中的 `SERVER_ID` 与 Portal 目标节点是否一致。

## English

### Summary

The Unix installation command generated by the legacy v1 Portal could no longer download the agent script and `wget` returned `404 Not Found`. After the download URL was repaired and installation completed, the new server still did not appear under its intended monitoring node.

### Impact

- New servers could not be installed using the command copied from the Portal.
- When an installation command from the wrong server row was used, the new agent was bound to an existing node and the intended new node received no metrics.
- The incorrect binding could also cause the existing node's metrics to be overwritten or alternate between two machines.

### Root cause

1. The v1 Portal hard-coded the installer URL as:

   ```text
   https://raw.githubusercontent.com/kadidalax/cf-vps-monitor/main/cf-vps-monitor.sh
   ```

   After the upstream `main` branch moved to v2, `cf-vps-monitor.sh` was no longer present at the repository root. The legacy Portal therefore continued generating a stale URL.

2. After repairing the download, the installation command was copied from an existing server row. Its `-s/--server-id` value and API key belonged to the existing node rather than the newly created node, so metrics were reported to the wrong destination.

### Remediation

1. Pin the v1 Portal's `baseScriptUrl` to the immutable release that still contains the legacy installer:

   ```text
   https://github.com/kadidalax/cf-vps-monitor/releases/download/v1.0.2/cf-vps-monitor.sh
   ```

2. Redeploy the Worker so commands copied from the Portal use the release asset directly.
3. Stop the incorrectly bound agent and copy a fresh installation command from the Portal row for the new server.
4. Confirm that both the server ID and API key belong to the intended node before reinstalling and starting the agent.

### Verification

- The release URL redirects successfully and returns the complete script.
- The downloaded script passes `bash -n` syntax validation.
- The production Portal's `admin.js` serves the corrected release URL.
- After reinstalling with the command generated for the correct node, the new node begins reporting metrics.

### Preventive actions

- Pin legacy installers to an immutable release or commit instead of a moving `main` branch path.
- Add a CI check that confirms every generated installer URL returns a successful response and a non-empty file.
- Include both the server name and server ID in the Portal's copy-success message to reduce wrong-row mistakes.
- Have the installer print the target Worker, server name, and server ID before installation, with either confirmation or a non-interactive validation option.
- During troubleshooting, first compare `SERVER_ID` in `$HOME/.cf-vps-monitor/config` with the intended Portal node.
